# 請求前の見直し（F1 MVP）

## 範囲と意味

- 一覧の「今後7日以内」は、利用者の設定タイムゾーンの**今日から7日後まで（両端を含む）**の次回請求のうち、未判断のものを表示する。対象がない場合は、同じ基準で30日後までの予定を案内する。
- 詳細で次回請求の「継続する / 見直す」を保存・変更・取消できる。30日より先の次回請求も詳細から判断できる。過去・任意の請求回をクライアントから指定して保存することはできない。
- 判断は SubTrack 内の記録のみ。外部サービスの解約・契約変更ではなく、既存の active / canceled 状態も変えない。解約URL・方法・メモへの既存導線を使う。
- 通知の追加、通知台帳や通知状態の変更、分析イベント・新料金・自動解約は含めない。既存の `?subscription=<id>` 通知リンクは同じ詳細を開く。
- 判断操作はオンライン専用。オフライン保存や自動再送キューは持たない。失敗時は保存済みとして表示せず、再接続後に再読込・再操作できる。

## データと競合

`subscription_review` は利用者・サブスク・date-only の請求日・判断・更新時刻・請求条件のスナップショットを持つ。`(subscription_id, billing_date)` は一意。利用者またはサブスクの削除に合わせて判断も削除する。

- 日付は既存の `billing-dates.ts` と設定タイムゾーンから求め、月末や閏年も元の初回請求日を基準にする。保存済み `nextBillingAt` やクライアントの時計は権威にしない。
- 金額・通貨・周期・初回請求日・契約状態の変更で、`tracked_subscription.review_revision` を増やす。値を以前と同じに戻しても過去の判断を復活させない。その他のメモ・通知設定等の変更だけでは判断を無効にしない。
- 次の請求日は別レコード。請求条件が変わった場合、同じ請求日に古い判断があっても未判断として表示する。再判断時は同じ一意キーのスナップショットを置き換える。MVPは完全な監査履歴を提供しない。
- 既存の作成時刻も比較トークンに含め、削除後にSQLiteが同じIDを再利用した別レコードへの古い要求を拒否する。
- サーバーがセッションから所有者を特定し、現在の請求条件・active状態・次回請求日を検証する。書込み時にも所有者/状態/条件を条件付きSQLで確認する。
- 更新時刻を競合トークンにし、古いタブからの異なる判断による上書きを防ぐ。同じ操作の再送は冪等。取消は削除ではなく `decision = NULL` の記録を残し、遅れて届く古い保存要求が判断を復活させるのを防ぐ。
- 取消時のNULLは「未判断」であり、外部サービスの解約を意味しない。

## リリース前の手順（このPRでは実行しない）

このリポジトリの `migrations/meta/_journal.json` は0017までで、0018〜0027の既存手動SQLを網羅していない。今回も**0028のみの手動・加算移行**とし、古いjournalやsnapshotを一括修復しない。`pnpm db:migrate:prod` だけで0028が適用されるとは考えない。過去SQLの再実行や `db:push:prod` はしない。

## ロールバック

- アプリだけを直前の既知の正常版へ戻す。追加カラム/テーブルを**残して**判断データを保全する。`DROP TABLE`、revisionカラム削除、履歴削除は通常のロールバックに含めない。
- 旧アプリ稼働中に請求条件や状態が編集されるとrevisionは更新されない。再リリースの前に、承認された移行で全サブスクのrevisionを1つ進め、保存済み判断を未判断に戻す（記録自体は残す）。例: `UPDATE tracked_subscription SET review_revision = review_revision + 1;`。この操作も本番の別途承認・バックアップ・検証が必要。
- スキーマ移行が途中で失敗した場合はコードを出さず、適用済み構造と履歴を調査する。データを消す「やり直し」や既存手動移行の全適用で修復しない。
